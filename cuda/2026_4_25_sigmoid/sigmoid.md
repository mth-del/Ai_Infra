# pack和unpack哪个比较好
结论先说：没有绝对谁更好，要看数据长度、对齐、尾部比例和你算子是算力瓶颈还是带宽瓶颈。
* pack（向量化打包，128-bit 读写）：

    大多数大张量、对齐好、N 足够大时更快
    优势来自更少的 load/store 指令、更高带宽利用率
    但实现复杂，尾部处理麻烦，对齐不对会掉速或出错

* unpack（标量逐元素）：

  代码简单、通用性强、边界安全
  小规模数据或尾部占比高时不一定比 pack 慢多少
  但在大规模内存带宽场景通常跑不过 pack

面试可这么答：

“我会用 pack 做主路径，unpack 做尾部回退。当 idx+vector_width-1 < N 且地址对齐时走 pack，否则走 unpack。这样同时保证吞吐和正确性。”

1) f32x4（float4 向量化）
好处：

一线程处理 4 个 FP32，减少 load/store 指令数
更容易吃满带宽（对齐好时）
结果表现：

小中规模有加速（如 1024x1024：0.020 -> 0.008ms）
大规模时和 torch 接近，甚至略慢（4096x4096）
说明进入了内存带宽/框架内核优化上限区间，你的 kernel 优势被抹平。
2) f16（标量半精度）
好处：

数据更小，理论带宽压力更低
结果表现：

稳定正确，但不一定快于 f16_th
标量版本通常仍受访存和指令开销限制
3) f16x8（每线程 8 half）
好处：

线程粒度更粗，减少调度/索引开销
向量化访存提升吞吐潜力
结果表现：

明显快于标量 f16（多数 case）
但很多 case 仍比 f16_th 略慢或持平，说明还没完全打赢框架优化路径
4) f16x8pack（128-bit pack load/store）
好处：

用宽访存一次搬更多数据（典型 128-bit）
理论上是你这里最“工程化”的向量路径
结果表现：

通常优于 f16x8（如 2048x4096, 4096x2048）
但在大规模仍经常接近/略逊 f16_th，说明：
可能已经接近带宽上限
或尾部/对齐/launch 开销还有改进空间
为什么会出现“优化了但不一定比 torch 快”
torch 的 sigmoid 内核本身高度优化（融合、向量化、调度成熟）
你现在测的是单算子，算术强度低，容易变成带宽瓶颈
当规模变大，大家都被带宽限制，手写 kernel 优势会缩小
你这次实验的核心结论（可写到 md）
向量化（x4/x8/pack）在小中规模有明显收益。
f16x2 路径结果全 0，需先修正确性（暂不纳入性能对比）。
大规模下瓶颈趋向内存带宽，手写 kernel 与 torch 差距缩小。
f16x8pack 是当前自定义实现里最有潜力的方向（在多数 case 优于其他手写 f16 路径）。
