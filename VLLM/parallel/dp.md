# 数据并行 DP 优化记录

## 1. 当前优化背景

当前示例模拟的是推理服务中的数据并行场景。

在大模型推理中，如果只有一个模型副本，所有请求都要排队进入同一个模型执行。即使外部同时来了多条请求，真正执行时仍然可能是串行的，整体耗时等于多条请求耗时的累加。

形象理解：

```text
单模型副本：只有一个窗口，所有人排一队办理业务。
多模型副本：开多个窗口，不同请求分到不同窗口同时办理。
```

当前 `dp.py` 对比了两个场景：

```text
场景 1：一个模型副本处理 4 条数据，整体串行执行。
场景 2：四个模型副本处理 4 条数据，每条数据分配给不同副本，并行执行。
```

优化目标是：

```text
通过增加模型副本，把多个独立请求分散到不同副本上并行处理，
减少整体等待时间，提高吞吐能力。
```

## 2. 优化方案

### 2.1 单模型副本基线

基线方案中只创建一个 `FakeModel`：

```text
model = FakeModel(1)
```

所有输入数据依次调用：

```text
model.process(data)
```

这种方式逻辑简单，但缺点明显：

```text
第 2 条数据必须等第 1 条数据处理完
第 3 条数据必须等第 2 条数据处理完
整体耗时接近所有请求耗时之和
```

### 2.2 多模型副本并行

优化方案中创建多个模型副本：

```text
models = [FakeModel(i + 1) for i in range(num_models)]
```

然后使用线程池并行提交任务：

```text
ThreadPoolExecutor(max_workers=num_models)
```

每条数据通过轮询方式分配到不同模型副本：

```text
model_idx = i % num_models
```

例如 4 条数据、4 个模型副本时：

```text
数据1 -> 模型副本1
数据2 -> 模型副本2
数据3 -> 模型副本3
数据4 -> 模型副本4
```

这样每个模型副本只处理一条数据，多个请求可以同时运行。

### 2.3 Future 异步收集结果

线程池的 `submit` 会立即返回一个 `Future`，不会阻塞等待模型处理完成。

```text
future = executor.submit(models[model_idx].process, data)
```

后面再通过：

```text
concurrent.futures.as_completed(future_to_data)
```

按完成顺序收集结果。

这种方式模拟了推理服务中的异步请求执行：

```text
请求先提交到执行队列
模型副本并行处理
谁先完成就先返回
```

## 3. 实验结果

本次实验使用 4 条模拟数据，每条数据的处理耗时通过 `random.uniform(0.1, 0.5)` 生成。

为了公平比较，单模型和多模型场景都设置了相同随机种子：

```text
random.seed(42)
```

实验结果：

```text
单个模型副本总耗时：0.866 秒
4 个模型副本总耗时：0.365 秒
加速比：2.37x
性能提升：57.8%
```

结果分析：

```text
单模型副本时，4 条数据串行处理，耗时接近 4 个任务耗时之和。
多模型副本时，4 条数据并行处理，整体耗时主要由最慢的那个任务决定。
```

形象理解：

```text
串行执行像 4 个人共用 1 个窗口，总时间是 4 个人办理时间相加。
并行执行像 4 个人分别去 4 个窗口，总时间主要取决于最慢的那个人。
```

## 4. 下一步优化策略

### 4.1 加入动态负载均衡

当前使用的是简单轮询策略：

```text
model_idx = i % num_models
```

如果不同请求耗时差异很大，可能出现某个模型副本很忙，而其他副本已经空闲。

下一步可以引入任务队列：

```text
空闲模型副本主动从队列中取任务
谁先处理完，谁继续拿下一条数据
```

这样可以减少长尾请求造成的资源浪费。

### 4.2 支持动态 batch

真实推理系统中，不一定是一条请求对应一次模型执行。

可以把短时间内到达的多个请求合并成一个 batch：

```text
多个小请求 -> 合并成一个 batch -> 一次模型 forward
```

这样可以提高 GPU 利用率，减少 kernel launch 和调度开销。

### 4.3 引入请求队列和调度策略

后续可以模拟 vLLM 中的调度逻辑：

```text
等待队列
运行队列
请求优先级
超时控制
最大 batch size
```

这样更接近真实大模型 serving 系统。

### 4.4 统计更多性能指标

当前只统计了总耗时和加速比。

后续可以补充：

```text
QPS：每秒处理请求数
平均延迟
P95 延迟
每个模型副本的利用率
队列等待时间
```

这些指标更适合评估推理服务性能。

### 4.5 从线程模拟扩展到真实 GPU 多副本

当前代码使用线程和 `FakeModel` 模拟模型推理。

下一步可以替换成真实模型：

```text
多个模型副本加载到不同 GPU
或者同一 GPU 上启动多个执行实例
对比单副本、多副本、动态 batch 的推理吞吐
```

一句话总结：

```text
当前优化验证了数据并行的核心思想：通过多个模型副本同时处理不同请求，把串行等待变成并行执行，从而降低总耗时、提升吞吐。
```
