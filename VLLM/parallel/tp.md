# 张量并行 TP 优化记录

## 1. 优化背景

当前 `tp.py` 演示的是大模型推理中的张量并行思想，重点是矩阵乘法的列切分。

在 Transformer 中，线性层本质上是矩阵乘法：

```text
C = A @ B
```

其中：

```text
A：输入 hidden states
B：线性层权重
C：输出 hidden states
```

当模型很大时，权重矩阵 `B` 也会很大。如果全部放在一张 GPU 上，会遇到两个问题：

```text
1. 单卡显存放不下完整权重
2. 单卡计算压力太大，推理速度慢
```

张量并行的核心思路是：

```text
把一个大矩阵拆成多份，分给多张 GPU 或多个计算单元并行计算。
```

形象理解：

```text
原来一张大试卷由一个人做；
现在把试卷按题目分成几部分，多个人同时做；
最后把每个人的答案拼起来，就是完整结果。
```

## 2. 优化思路

### 2.1 对权重矩阵按列切分

代码中定义了两个矩阵：

```text
A shape = (M, N)
B shape = (N, K)
```

完整矩阵乘法结果是：

```text
C = A @ B
C shape = (M, K)
```

当前示例中：

```text
M = 3
N = 4
K = 6
```

然后把 `B` 按列切成 3 份：

```text
B_0 shape = (N, K/3)
B_1 shape = (N, K/3)
B_2 shape = (N, K/3)
```

也就是：

```text
B = [B_0, B_1, B_2]
```

### 2.2 每个分片独立计算

切分后，每个分片都可以独立计算：

```text
C_0 = A @ B_0
C_1 = A @ B_1
C_2 = A @ B_2
```

这些计算之间没有依赖关系，所以可以并行执行。

在真实张量并行中，可以理解为：

```text
GPU 0 计算 A @ B_0
GPU 1 计算 A @ B_1
GPU 2 计算 A @ B_2
```

这样每张 GPU 只保存一部分权重，也只负责一部分输出。

### 2.3 AllGather 拼接结果

因为 `B` 是按列切分的，所以每个局部结果 `C_i` 对应最终输出的一部分列。

最后只需要按列拼接：

```text
C_final = concat([C_0, C_1, C_2], axis=1)
```

就可以还原完整输出：

```text
C_final = A @ B
```

这个过程在分布式系统里类似 `AllGather`：

```text
每个 rank 算出一部分输出
然后把所有 rank 的输出收集并拼接
```

## 3. 优化结果

本次脚本运行后，验证结果为：

```text
验证一致性: True
```

说明：

```text
先把 B 按列切分
再分别计算 A @ B_i
最后把局部结果按列拼接
```

得到的 `C_final` 和直接计算 `A @ B` 的结果完全一致。

实验中的形状变化如下：

```text
A: (3, 4)
B: (4, 6)

B_0: (4, 2)
B_1: (4, 2)
B_2: (4, 2)

C_0: (3, 2)
C_1: (3, 2)
C_2: (3, 2)

C_final: (3, 6)
```

优化收益可以总结为：

```text
1. 每个设备只保存一部分权重，降低单卡显存压力
2. 多个分片可以并行计算，提高整体吞吐
3. 列切分后只需要拼接输出，不需要对局部结果做求和
```

形象理解：

```text
列切分就像把输出通道分给不同 GPU。
每张 GPU 负责生成一部分输出通道，
最后把这些输出通道拼起来，就是完整线性层输出。
```

## 4. 进一步优化

### 4.1 支持真实多 GPU 通信

当前代码使用 `numpy` 在单进程里模拟切分和拼接。

下一步可以扩展为真实多 GPU：

```text
每个 GPU 加载一份 B_i
每个 GPU 计算自己的 C_i
通过 NCCL AllGather 收集结果
```

这样更接近 Megatron-LM、vLLM、TensorRT-LLM 中的 Tensor Parallel。

### 4.2 增加行切分对比

当前示例是列切分。

还可以补充行切分：

```text
B 按行切分
A 也按对应维度切分
每个分片计算局部结果
最后通过 AllReduce 求和
```

对比关系：

```text
列切分：局部结果按列拼接，通常需要 AllGather
行切分：局部结果形状相同，通常需要 AllReduce
```

### 4.3 加入通信开销分析

张量并行不只是计算切分，还会引入通信成本。

后续可以记录：

```text
计算时间
AllGather 时间
AllReduce 时间
通信数据量
不同切分数下的加速比
```

如果通信成本太高，增加 GPU 数量不一定继续加速。

### 4.4 结合 Transformer 线性层

下一步可以把这个示例映射到真实大模型结构：

```text
QKV Projection
Attention Output Projection
MLP Up Projection
MLP Down Projection
```

比如：

```text
QKV / Up Projection 适合列并行
Output / Down Projection 常用行并行
```

这样可以更好理解大模型推理框架里的 TP 设计。

### 4.5 增加性能指标

当前只验证了数值一致性。

后续可以补充：

```text
单卡完整矩阵乘法耗时
多分片并行计算耗时
通信耗时
显存占用
加速比
```

一句话总结：

```text
当前代码验证了张量并行中的列切分思想：把权重矩阵按输出维度拆分，多个分片独立计算，最后通过拼接得到完整输出，从而降低单卡显存压力并提升并行计算能力。
```

### 5.2 最新实验现象

修复后脚本可以完整运行，但从图中可以看到：

```text
CPU 上的 Python 线程版张量并行，大多数情况下比标准 numpy 矩阵乘法更慢。
```

这不是张量并行思想错误，而是当前实验环境和实现方式导致的。

原因主要是：

```text
1. np.dot 底层已经调用高性能 BLAS，通常已经做了多线程、SIMD 和 cache blocking。
2. 手写 TP 版本额外引入线程创建、任务分发、join 同步和结果写回开销。
3. 当前是在同一台 CPU 上开多个 Python 线程，不是真正的多 GPU 并行。
4. 多个线程会竞争同一套 CPU cache 和内存带宽。
5. 小矩阵计算时间太短，线程调度开销可能超过并行收益。
```

形象理解：

```text
真实 TP 是多张 GPU 分担一个大矩阵；
当前实验是多个 Python 线程抢同一台 CPU。
所以它主要用于验证“列切分 + 局部计算 + 拼接”的正确性，不适合作为真实 TP 性能结论。
```

### 5.3 当前结论

当前代码的价值是教学和原理验证：

```text
它证明了列切分后，每个分片可以独立计算，最后按列拼接能得到和完整矩阵乘法一致的结果。
```

但当前代码不能证明 CPU 线程版 TP 一定更快。

真正的张量并行收益通常来自：

```text
1. 多 GPU 分担显存压力
2. 多 GPU 并行执行大矩阵乘法
3. 使用 NCCL 做高效 AllGather / AllReduce 通信
4. 与 Transformer 中 QKV、MLP 等大线性层结合
```

面试表达可以这样说：

```text
我用 Python 线程模拟 TP 时发现并行版本反而更慢，因为 numpy baseline 已经高度优化，而线程版会引入调度和内存竞争开销。这个实验主要验证 TP 的切分正确性；真实大模型 TP 应该放到多 GPU 上，通过权重切分、并行 GEMM 和 NCCL 通信获得显存和吞吐收益。
```
